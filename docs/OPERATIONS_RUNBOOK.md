# Axly Studio production operations runbook

Use this checklist for releases, smoke tests, incidents, rollbacks and recovery. Store release evidence with the deployment record. Never paste tokens, passwords, database URLs, full customer payloads or other secrets into tickets or logs.

## 1. Release prerequisites

- Identify the exact commit SHA and confirm it is the intended release on the default branch (currently master).
- Review code and docs together. Changed routes, environment variables, bot commands, migrations or domain assumptions must have matching documentation/tests.
- Run backend tests, bot tests, frontend lint and frontend build locally.
- Confirm GitHub Actions jobs pass for the exact commit, not an earlier SHA.
- Confirm access to Vercel, Render and the database dashboard and know the rollback target.
- Check backup status and ensure a recovery procedure has been tested for the database.
- Review migrations. Backend startup runs migrations before listening; a deployment rollback does not automatically roll back database changes.
- Confirm secrets are stored in hosting secret settings, not committed source.
- Verify domain configuration, TLS and API proxy behavior before announcing a release.

## 2. Local validation

Run from each package directory:

```bash
# Backend
cd backend
npm ci
npm test

# Frontend
cd frontend
npm ci
npm run lint
npm run build

# Telegram bot
cd telegram-bot
npm ci
npm test
```

GitHub Actions currently runs backend tests against PostgreSQL, bot tests and frontend build. Frontend lint is a local release check but is not currently a CI job.

## 3. Deploy settings

| Component | Expected settings | Notes |
|---|---|---|
| Website / Vercel | Root frontend; build npm run build; output dist/ | frontend/vercel.json contains the API rewrite and SPA fallback |
| API / Render documented target | Root backend; install npm ci; start npm start | Set production environment, database and security values |
| Telegram bot / separate service | Root telegram-bot; install npm ci; start npm start | Set token, API URL, frontend URL, shared secret and mode |
| Database | PostgreSQL provider chosen for the environment | Configure TLS/credentials from that provider |

These are repository guidelines, not proof of current dashboard values. Check service, branch, build limits, domains and environment settings in the live dashboards.

## 4. Domain and routing tests

Canonical website intent is https://studio.axly.in. The secondary https://url.axly.in host should permanently redirect to https://studio.axly.in. Short links use the host configured in SHORT_DOMAIN, expected to be https://s.axly.in when routing is configured.

```bash
curl -sS -I https://studio.axly.in/
curl -sS -I https://url.axly.in/
curl -sS -I "https://url.axly.in/example-path?probe=1"
curl -sS -i https://studio.axly.in/api/health
```

Check the actual status and Location header, not just domain validation:
- studio.axly.in should serve the site over HTTPS.
- url.axly.in should redirect permanently to studio.axly.in. Confirm it does not redirect to itself and preserves the intended path/query.
- Public /api/health through studio.axly.in should reach the backend through the Vercel rewrite.
- s.axly.in must reach the short-link handler and match the hostname generated by the API.

**Custom-domain caveat:** backend/src/controllers/domainController.js currently uses url.axly.in as the CNAME target for page-type custom domains and api.axly.in for short-link domains. Since url.axly.in is intended to be redirect-only, test custom page-domain routing end to end before treating it as production-ready. If the target is changed, update code and customer-facing instructions in the same change.

## 5. Health and smoke checks

```bash
curl -i https://api.axly.in/healthz
curl -i https://api.axly.in/readyz
curl -i https://api.axly.in/api/health
```

- /healthz is liveness only.
- /readyz queries the database; HTTP 503 means not ready.
- /api/health reports API/database health.
- Test through the public website proxy as well as the direct API origin.

Using a disposable account and test destination:
1. Register/login and retrieve the current user.
2. Create a short link, open it and verify the destination/status.
3. Generate and open a QR code.
4. Publish/open a test public page.
5. Load analytics and confirm an intentional test click.
6. Verify API-key flows using a disposable least-privilege key if enabled.
7. Clean up test artifacts when safe.

## 6. Telegram release checks

1. Confirm startup logs show Telegram getMe success, command-menu registration and polling/webhook activation.
2. Bot GET /healthz should return 200 after initialization; 503 means not ready.
3. Check backend /readyz separately.
4. Test /start, /help, /shorten, /alias with a linked account, /qr, /mylinks, /stats, /account, /settings and /cancel.
5. Test inline buttons, forwarded URL messages, multi-URL messages and prompt cancellation.
6. Ensure only one long-polling process uses a bot token. For webhook mode, check HTTPS domain and webhook secret configuration.

Bot health is not proof that API/database calls succeed.

## 7. Secret rotation

If a secret may be exposed, rotate immediately and inspect access/logs.

- Telegram token: rotate via BotFather, update bot service settings, restart, verify getMe.
- TELEGRAM_BOT_SECRET: coordinate the update in backend and bot settings; both must use the same new value. Verify account linking.
- JWT_SECRET: plan for existing sessions to become invalid; verify login/session behavior after the change.
- VISITOR_SALT: rotation changes unique-visitor deduplication continuity; record why and when.
- API key: revoke or rotate through key management. Capture the replacement secret directly into a secret store.
- Webhook signing secret: rotate and update the receiver before expecting signed deliveries to validate.
- Database credentials: rotate via the provider, update services and verify readiness before removing old credentials.

Never include raw secret values in issues, screenshots or commit messages.

## 8. Backup and restore

Verify the selected database provider's backup schedule, retention, access and recovery options in its dashboard. This repository does not prove that automated production backups are configured. Define and record recovery point objective (RPO) and recovery time objective (RTO), and perform a restore drill.

```bash
pg_dump "<DATABASE_URL>" --format=custom --file="axly_backup_YYYYMMDD_HHMMSS.dump"
```

Replace the placeholder with the authorized database URI in a secure shell. Restore only into a confirmed non-production target first:

```bash
pg_restore --clean --if-exists --no-owner --dbname="<RESTORE_DATABASE_URL>" axly_backup.dump
```

Never restore over production as the first test. Verify schema, extensions, privileges, ownership handling and critical application reads. Securely delete temporary backups containing customer data after the drill and record the outcome.

## 9. Rollback

- **Frontend:** use the Vercel rollback/promote function to return to a known-good deployment; recheck env, domains and API rewrite.
- **API or bot:** redeploy the last known-good deployment/commit. Verify settings and health checks.
- **Database:** code rollback does not reverse migrations. Assess the migration first; use a tested restore or forward-fix plan. Do not replace production data without an explicit incident decision and backup.
- After rollback, repeat health checks and end-to-end smoke tests.

## 10. Incident triage

### Website/build failure
- Inspect Vercel logs for the exact commit.
- Separate source/test failure from environment/dependency/hosting build-rate-limit failure.
- Check domain assignment and TLS.
- Test /api/health through the website proxy; if direct API works but proxy fails, inspect frontend/vercel.json.

### API or database unavailable
- Check Render state and logs.
- Call /healthz, /readyz and /api/health.
- Verify DB credentials/TLS/network access, migration startup and pool limits.
- Never paste the database URL into incident notes.

### Bot not responding
- Check bot /healthz, startup logs, token, outbound network and polling/webhook state.
- Confirm only one polling instance.
- Verify backend readiness and matching TELEGRAM_BOT_SECRET.

### Redirect failure
- Check DNS, TLS, status and Location headers.
- Confirm url.axly.in redirects to studio.axly.in without a loop.
- Confirm s.axly.in reaches the short-link handler.
- Change one hosting/DNS layer at a time and repeat tests.

## 11. Release record

Record date/time, operator, repository/commit SHA, CI results, hosting deployment IDs/URLs, migration and backup evidence, domain tests, API/bot health, smoke-test results, rollback target and outstanding issues.

Do not label a release production-approved while required checks fail or critical domain/API behavior and recovery readiness remain unverified.
